## Quick Start
```
# Compile the main.cpp file
 ./scripts/build_native.sh
# Train
./Quadtrix data/input.txt
# Train from JSON with lower RAM settings
GPT_MODEL_PATH=/tmp/quadtrix-json.bin ./Quadtrix data/dataset.json --batch-size 1 --block-size 64 --max-iters 100 --eval-interval 200 --eval-iters 1 --skip-initial-eval --threads 4 --math-backend auto
# Train from JSON with strict packed int8 weights
./Quadtrix data/dataset.json --weight-storage int8 --activation-quant-bits 8 --optimizer-state-bits 8 --strict-quantized-weights --grad-clip 1.0 --batch-size 1 --block-size 64 --threads 4
# Output
./Quadtrix data/input.txt --generate
# Web UI
./Quadtrix --web --web-host 127.0.0.1 --web-port 8080
# Convert a completed compatible Qwen3 checkpoint to llama.cpp GGUF
./Quadtrix --convert-to-gguf models/profile/qwen3.bin --export-gguf models/profile/qwen3.gguf --gguf-outtype q8_0
# Tiny Qwen3 smoke training with the embedded Qwen tokenizer
./Quadtrix data/dataset.json --arch qwen3 --tokenizer qwen3 --n-embd 64 --n-head 4 --n-kv-head 2 --head-dim 16 --n-layer 2 --intermediate-size 192 --block-size 32 --batch-size 1 --max-iters 2 --skip-initial-eval --no-generate-after-train
# Build or validate the reusable Qwen token cache, then exit
./Quadtrix data/general_knowledge_100mb.txt --arch qwen3 --tokenizer qwen3 --tokenize-only --token-cache auto --tokenization-mode records
```
# Dataset notes
English: The native trainer now loads `.txt`, `.json`, JSONL, and a dependency-free native Parquet metadata/shard path. JSON examples should contain `instruction`, `input`, and `output`; the loader formats them into an instruction/response text template and stores one compact token corpus using `uint8_t` when the vocab fits or `uint16_t` otherwise. Huge `.txt` files stream in two passes to avoid keeping duplicated raw text in RAM. Parquet never calls Python or runtime converters; unsupported page codecs/encodings fail bilingually while full page decoding is completed. The optimized build script probes phone CPU flags, OpenMP, and optional BLAS/OpenBLAS but avoids `-mcpu=native`/`-march=native` by default; use `QUADTRIX_NATIVE_CPU=1` only for same-device builds. For Android app prebuilts, run `/home/manu/.gemini/antigravity/scratch/build_android_binaries.sh --only trainer` to produce `libquadtrix_trainer_baseline.so`, `libquadtrix_trainer_dotprod.so`, and `libquadtrix_trainer_armv9.so` with real tier CPU flags and guarded dot-product int8 matmul in dotprod-capable builds. Training can choose CPU cores with `--threads N`, accumulate microbatches with `--grad-accum-steps N`, choose `--math-backend auto|builtin|blas`, skip expensive startup eval with `--skip-initial-eval`, and use `--optimizer adamw|adamw16|adamw8|adamw4|sgd`. Preferred strict quantized base-model training uses `--weight-storage int8|int4`, `--activation-quant-bits 8|4`, `--optimizer-state-bits 32|16|8|4`, `--strict-quantized-weights`, and default `--grad-clip 1.0`; all trainable weights are packed int8/int4 tensors with scales and no persistent float32 master copy. Quantized v2 checkpoints save packed weights directly. Qwen3 training uses `--arch qwen3 --tokenizer qwen3`, embedded real Qwen tokenizer data, uint32 tokens, full RMSNorm/RoPE/GQA/SwiGLU backward, data-parallel RPC workers, and can export llama.cpp GGUF with `--export-gguf` or convert later with `--convert-to-gguf CHECKPOINT --export-gguf OUT.gguf`; the real 151,936-token softmax is expensive, so begin with tiny shapes. Quadtrix character checkpoints are rejected because their architecture/tokenizer do not match Qwen3. Relative models/checkpoints are stored under `models/<profile>/`. The web UI can upload/select datasets, save named option profiles into `profiles/`, start/stop/resume training gracefully, copy/clear logs, zoom/scroll the graph, show representative axis labels, show ETA plus average/latest seconds per iteration, show RAM/temperature/battery telemetry and diagnostics with Android dumpsys fallbacks when sysfs is blocked, edit runtime/model/quantization/distributed/GGUF options, view logs, and generate/chat from saved models with generation logs.

Qwen token cache / Cache de tokens Qwen: English: Qwen3 runs can use `--token-cache auto|off|rebuild` and `--token-cache-dir PATH` to reuse a native `.qtok` corpus keyed by tokenizer, dataset metadata, format, columns, and tokenization mode. `--tokenize-only` builds or validates the cache and exits, while `--tokenize-log-interval-sec N` controls progress logs. The default `--tokenization-mode records` extracts newline-group TXT records or formatted JSON/Parquet records, tokenizes each record independently, and inserts EOS between records; this is the safe mode for distributed tokenization because workers receive complete records instead of byte slices. `whole` keeps the older local-only stream behavior and logs a warning for large inputs. Espanol: Las ejecuciones Qwen3 pueden usar `--token-cache auto|off|rebuild` y `--token-cache-dir RUTA` para reutilizar un corpus nativo `.qtok` identificado por tokenizer, metadatos del dataset, formato, columnas y modo de tokenizacion. `--tokenize-only` crea o valida el cache y sale, mientras `--tokenize-log-interval-sec N` controla los logs de progreso. El default `--tokenization-mode records` extrae registros TXT por grupos de lineas o registros JSON/Parquet formateados, tokeniza cada registro de forma independiente e inserta EOS entre registros; es el modo seguro para tokenizacion distribuida porque los workers reciben registros completos en vez de cortes de bytes. `whole` conserva el comportamiento local legacy de stream completo y avisa con entradas grandes.

Distributed Qwen cache / Cache Qwen distribuido: English: after a coordinator builds or loads a Qwen `.qtok`, it checks active workers and sends the cache file before train-step RPC begins. Reconnected or newly added workers are checked again and receive the cache if missing. Train-step payloads carry the coordinator cache key, so workers load the same cache instead of deriving a different key from `worker_datasets/`. Espanol: despues de que el coordinador crea o carga un `.qtok` Qwen, revisa los workers activos y envia el archivo cache antes de empezar los RPC de entrenamiento. Los workers reconectados o agregados se revisan otra vez y reciben el cache si falta. Los payloads de train-step llevan la clave de cache del coordinador, asi los workers cargan el mismo cache en vez de derivar una clave distinta desde `worker_datasets/`.

Distributed RPC / RPC distribuido: English: the same `quadtrix` binary can run workers with `--worker-only --worker-host 0.0.0.0 --worker-port 9091 --worker-token TOKEN`; a host/port-only command is inferred as worker mode and refuses to continue without a token instead of starting default training. A coordinator using `--dist-mode data-parallel` streams regular dataset files once into each worker's `worker_datasets/` cache, sends model snapshots, receives compact gradient payloads, averages them with the local gradient, clips once, and applies one optimizer update. In distributed data-parallel mode `--grad-accum-steps` is the global accumulation target, so one worker plus coordinator with `--grad-accum-steps 20` runs about 10 microsteps on each device and merges a weighted 20-microstep update. Worker work share is weighted by advertised CPU threads using a softened square-root curve. If a worker disconnects during an iteration, the coordinator redistributes its unfinished microsteps to remaining online workers before falling back to local coordinator work. Offline workers are retried with `--dist-reprobe-interval`; when one reconnects, the coordinator asks it to verify the cached dataset and resends the file if it is missing or the check cannot be trusted. `--dist-rpc-timeout-sec` controls how long a slow train-step RPC may run before it is considered failed. Use `--dist-workers-file profiles/name.workers.txt` to change workers while the coordinator is already training; plain `host:port` entries remain active, `1 host:port` means active, and `0 host:port` keeps a saved but disabled row. The WebUI manages that file as one row per worker with an active toggle, save, and remove control. ETA in the WebUI uses server-persisted `ETA` and `maxIter` parsed from training logs, so other devices no longer calculate a different value from their local form defaults. Worker terminals log status requests, dataset checks, dataset chunks, cache loads, train steps, losses, and gradient payload sizes. Use `--dist-coordinator-compute 0` when the coordinator should only coordinate and not contribute local train gradients. Espanol: el mismo binario `quadtrix` puede ejecutar workers con `--worker-only --worker-host 0.0.0.0 --worker-port 9091 --worker-token TOKEN`; un comando con solo host/puerto se infiere como modo worker y se niega a continuar sin token en vez de iniciar entrenamiento por defecto. Un coordinador con `--dist-mode data-parallel` envia archivos de dataset regulares una vez al cache `worker_datasets/` de cada worker, envia snapshots del modelo, recibe payloads compactos de gradientes, los promedia con el gradiente local, recorta una vez y aplica una actualizacion del optimizador. En data-parallel distribuido `--grad-accum-steps` es el objetivo global de acumulacion, asi que un worker mas coordinador con `--grad-accum-steps 20` ejecuta unos 10 microsteps en cada dispositivo y fusiona una actualizacion ponderada de 20 microsteps. La porcion de trabajo de workers se pondera por hilos CPU anunciados usando una curva suavizada de raiz cuadrada. Si un worker se desconecta durante una iteracion, el coordinador redistribuye sus microsteps sin terminar a workers online restantes antes de caer a trabajo local del coordinador. Los workers offline se reintentan con `--dist-reprobe-interval`; cuando uno reconecta, el coordinador le pide verificar el dataset cacheado y reenvia el archivo si falta o la revision no es confiable. `--dist-rpc-timeout-sec` controla cuanto puede durar un RPC lento de train-step antes de considerarlo fallido. Usa `--dist-workers-file profiles/nombre.workers.txt` para cambiar workers mientras el coordinador ya entrena; las entradas planas `host:port` siguen activas, `1 host:port` significa activo, y `0 host:port` conserva una fila guardada pero desactivada. La WebUI maneja ese archivo como una fila por worker con toggle activo, guardar y quitar. El ETA en la WebUI usa `ETA` y `maxIter` persistidos por el servidor desde los logs de entrenamiento, asi otros dispositivos ya no calculan un valor distinto desde sus defaults locales del formulario. Las terminales de workers muestran solicitudes de estado, revisiones de dataset, chunks de dataset, cargas de cache, pasos de entrenamiento, perdidas y tamanos de payload de gradientes. Usa `--dist-coordinator-compute 0` cuando el coordinador solo debe coordinar y no aportar gradientes locales.

Model note / Nota de modelo: new checkpoints include a compatibility header. Use compatible dataset and runtime settings when resuming, chatting, or generating; old raw checkpoints still require manual care.
